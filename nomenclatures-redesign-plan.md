# План реализации: редизайн страницы `/nomenclatures`

**Объём:** каталог (Toolbar + список карточек + сайдбар) + SEO-секции (Hero, популярные города, форматы, преимущества, «кому подходит», шаги, CTA, SEO-текст, FAQ).
**Вне объёма:** Header и Footer — уже есть в глобальном layout, не трогаем.
**Источник дизайна:** мокап на Tailwind Play (HTML/Tailwind v4 классы).
**Затрагиваемые файлы (уже видел):** `page.tsx`, `Toolbar.tsx`, `NomenclatureWrapper.tsx`.

## 0. Важно прочитать перед началом

### 0.1. Конфликт скролла — главный архитектурный риск

Сейчас `NomenclaturesPage` — это **app-shell с фиксированной высотой**, а не обычная скроллящаяся страница:

```
<div className="flex flex-col h-full w-full p-1 gap-2">
  ...
  <div className="grow min-h-0 overflow-hidden">   // фиксированная высота, обрезает контент
    <div className="h-full">
      <NomenclatureWrapper .../>
    </div>
  </div>
</div>
```

А внутри `NomenclatureWrapperContent` инфинити-скролл завязан именно на **внутренний скролл контейнера**, а не на скролл окна:
- `IntersectionObserver({ root: cardsWrapperRef.current, ... })`
- fallback по scroll-событию вешается на `cardsWrapperRef.current`, а не на `window`
- `ScrollButton scrollContainerRef={cardsWrapperRef}` — тоже завязан на этот же контейнер

Мокап — обычный длинный лендинг с обычным скроллом страницы (Hero → SEO-блоки → каталог → форматы → ... → FAQ), где каталог — всего лишь один из блоков. Это **несовместимо** с текущей моделью «список скроллится сам внутри себя».

**Нужно решить и явно закодировать одно из двух:**

| Вариант | Что меняется |
|---|---|
| **A. Каталог скроллится вместе со страницей (рекомендуется, т.к. так и в мокапе)** | Убрать `h-full/overflow-hidden/min-h-0` из `page.tsx`; `IntersectionObserver root` → `null` (viewport); scroll-fallback → слушать `window`; `ScrollButton` → скроллить `window`, а не контейнер |
| **B. Каталог остаётся «окном» с внутренним скроллом внутри лендинга** | Оставить текущую механику, но обернуть карточную зону в контейнер с фиксированной высотой (`max-h-[…] overflow-y-auto`) — визуально это будет отличаться от мокапа (там список — часть обычного потока страницы) |

Без явного решения этого пункта весь остальной рефакторинг рискует «не завестись» (инфинити-скролл просто не сработает, потому что root-контейнер перестанет существовать или изменит форму).

## 2. Что меняется в `Toolbar.tsx`

Текущая структура: верхняя панель (`totalItems` + `SearchForm` + иконка-тоггл `FiltersPanel`) и отдельно ряд с кнопкой «Торговый центр» + `CitiesSlider`.

Мокап предлагает более развёрнутый, всегда видимый фильтр-бар:
- строка: поле поиска + 3 select'а (город / тип площадки / стоимость) + кнопка «Найти»
- под ней: ряд чипов быстрых фильтров + кнопки «Сбросить» / «Выбрать все»

**Важные несостыковки, которые нужно решить до кодинга:**

1. **Select «Город»** — сейчас в `searchParams` (`page.tsx`) нет параметра `city`, есть `brand_name`/`brand_id`. Уточнить у бэкенда/типов: город — это отдельное поле фильтрации или он зашит в `search`/`brand_id`? Если нет готового API-параметра — фильтр по городу в новом баре нельзя сделать «как в мокапе» без доработки API.
2. **Select «Стоимость»** — такого параметра в `NomenclaturesPageProps.searchParams` нет вообще. Нужно либо добавить (и на бэкенде, и в `page.tsx`/`url.searchParams`), либо не включать этот фильтр в первую итерацию.
3. **Чипы «Аудиореклама» / «Видеореклама» / «До 200 ₽/день»** — в текущем коде нет параметра формата рекламы. Чип «Торговый центр» уже реализован через `type_of_place` (`buildTcUrl`, `isTcActive`) — **эту логику просто переносим в новую вёрстку без изменений**, остальные чипы — по факту наличия соответствующих полей в API.
4. **«Выбрать все»** в мокапе стоит рядом с «Сбросить» в блоке фильтров — но в проекте уже есть `SelectAllButton` в `NomenclatureWrapper`, который, судя по расположению («Всего найдено: N» + кнопка), скорее всего про выбор карточек (для медиаплана/корзины), а не про фильтры. **Это разные вещи с одинаковым названием в мокапе** — нужно решить: либо переименовать одну из кнопок, либо в фильтр-баре убрать «Выбрать все» и оставить только «Сбросить» (сброс фильтров), а существующий `SelectAllButton` оставить как есть в шапке списка.
5. Иконка фильтров (`SlidersHorizontal`) и модалка `FiltersPanel` — если новый бар покрывает основные фильтры инлайн, `FiltersPanel`, вероятно, остаётся для **дополнительных/редких** полей (`status`, `brand_id` и т.п., которых нет в новом баре). Не выпиливать `FiltersPanel`, пока не подтверждено, что все её поля перекрыты новым баром.

**Что переносится без изменений (готовая логика, просто новая обёртка/стили):**
- `handleLimitChange`, `toggleFilters`, `toggleLimitOptions`
- `handleTypeOfPlaceChange`, `buildTcUrl`, `isTcActive` — квик-фильтр «Торговый центр»
- `SearchForm` (сам компонент, возможно с новыми classNames под мокап)
- `CitiesSlider` — либо остаётся отдельным рядом (как сейчас), либо переезжает в секцию «Популярные города» / select «Город», если данные пересекаются — решить, не дублируется ли источник городов

## 6. Технические договорённости

- Tailwind v4 уже используется в проекте (видно по `text-xl!` в `page.tsx`) — новые секции пишем на утилитах Tailwind, без новых SCSS-модулей, если это не противоречит текущим конвенциям.
- Существующие компоненты на SCSS-модулях (`Toolbar.module.scss`, `NomenclatureWrapper.module.scss`) не переписывать полностью «на всякий случай» — точечно заменять/дополнять только те классы, что реально меняются визуально.
- Query-параметры страницы (`limit, page, search, brand_name, brand_id, status, type_of_place`) — контракт с бэкендом, новый UI фильтров обязан продолжать писать/читать эти же параметры (плюс новые — только после ответа на открытые вопросы 2–3).
- Один `<h1>` на страницу (см. п. 5.10).
- Все новые статические секции — серверные компоненты (без `'use client'`); `'use client'` — только там, где реально нужен интерактив (как сейчас в `Toolbar.tsx`/`NomenclatureWrapper.tsx`).
- Доступность: `label`/`aria-label` на инпутах и селектах фильтр-бара, `<details>`/`<summary>` для FAQ — ок для нативной доступности, либо использовать имеющийся в проекте аккордеон-компонент, если такой уже есть.
